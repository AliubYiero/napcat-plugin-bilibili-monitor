# ADR 0012: WebUI 监听状态页直接写监听与上限

日期: 2026-10-20
状态: 已采纳

## 背景

新增的监听状态页需要增删直播/动态监听、切换同接监听、调整会话上限。插件自带
WebUI 页面走无鉴权路由 (`getNoAuth` / `postNoAuth` / `deleteNoAuth`), 没有 QQ
身份; 此前的写操作只有会话启停, 风险较低。监听记录与上限是持久化业务数据,
在 WebUI 开放写入前必须明确信任边界与副作用。

候选方案: 页面要求填写 QQ 并按 `adminUsers` 判定 (身份可伪造); 只开放删除/提额
(新增仍回 QQ 指令, 体验割裂); 保持只读 (状态可见但不可操作); WebUI 视为超级
管理员。

## 决策

1. **WebUI 视为超级管理员**。写路由全部为无鉴权路由, 不传操作者身份; 信任边界
   是 NapCat 宿主登录。后端记录操作日志, 不做按操作者的权限细分。
2. **新增静默写入服务** (`monitorWriteService`): 复用 store、上限服务与 B 站校验,
   但**不发 QQ 消息、不触发立即推送**。
3. **添加基线与指令一致**: 直播只写房间快照作基线, 不补推开播卡片; 动态记录
   当前一页动态 id, 不补推旧动态。
4. **多目标新增逐目标执行**: 部分成功即返回逐目标结果, 一个会话超限不阻断其他
   会话。
5. **首版不做**批量操作、开播 @ 订阅编辑、导入导出。
6. **目标选择器展示禁用会话**: 加「指令已禁用」标注并提示「推送不受影响」, 不修改
   会话启用开关的现有语义 (见 ADR 0006)。

## 理由

- 无鉴权路由已经把信任边界放在宿主登录上; 再套一层可伪造的 QQ 身份没有实际
  安全收益, 只会增加操作摩擦。
- WebUI 操作不应在 QQ 会话里制造「已开始监听」噪音, 也不应因为主播正在直播就
  补推一张开播卡片; 推送应由真实状态变化触发。
- 逐目标结果与「按主播聚合、目标独立」的存储结构一致, 失败原因也能精确到会话。
- 指令链路与 WebUI 写链路共享 store 语义, 但**不共享发送副作用**, 避免 WebUI
  需求反向污染指令 service 的签名。

## 后果

- 任何能打开 NapCat 宿主面板的人都能修改监听与上限; 不提供按操作者的审计或
  权限细分。若未来出现多租户/多人运维需求, 需修订本 ADR。
- 写入失败只返回结构化结果, 不再依赖「回复消息」传达; 前端必须展示逐目标原因。
- 现有指令 service 与 WebUI 静默 service 会有少量校验逻辑重复; 禁止把静默分支
  塞回指令 service 的发送路径, 也禁止 WebUI 直接调用会发消息的指令 service。
- 会话启用开关仍只门控指令响应, 不门控推送 (见 ADR 0006 与 `CONTEXT.md`)。
- 相关范式: `webui-config-pattern.md` (监听状态页与端点)、`docs/monitors-page-plan.md`
  (任务拆分)。
