# ADR 0013: 监听健康快照只存内存

日期: 2026-10-20
状态: 已采纳

## 背景

监听状态页需要展示直播/动态轮询的上次执行、下次执行、失败原因, 以及动态监听
逐主播的最近检查结果。数据文件拓扑已由 ADR 0007 固定 (6 个业务文件 + 1 个会话
配置), 不允许自行新增文件; 现有直播房间数据与动态运行时数据承载的是业务快照,
不是运维元数据。

候选方案: 现场请求 B 站接口校验 (引入风控与时延); 扩展现有运行时文件持久化
健康字段 (重启不丢, 但污染业务快照语义); 不展示轮询健康 (运维盲区)。

## 决策

1. **新增纯内存健康快照单例** (`healthSnapshot`), 进程启动即为「未知」, 由直播/
   动态轮询服务在每轮开始、成功、失败时更新。
2. **动态监听额外维护逐主播内存 Map** (最近检查/成功/错误), 与动态轮询服务
   同生命周期, 不写入 `bilibiliDynRuntimeData.json`。
3. **渲染服务采用按需探测**: 页面打开或手动刷新时主动渲染一张极小 SVG, 结果
   缓存 60s, 不进入 10s 页面轮询, 也不建立独立定时器。
4. **不新增数据文件, 不修改现有数据文件结构**; 健康信息一律标注「本次进程内」,
   插件重载后显示「未知/尚未执行」。
5. **空闲与异常必须区分**: 无监听对象时轮询显示「空闲 (无监听)」; 未登录导致
   动态轮询跳过时显示「跳过 (未登录)」, 不作为故障。

## 理由

- 健康信息描述的是「当前进程是否正常」, 持久化后重启会显示过期结论, 反而误导
  运维。
- 不碰数据文件拓扑, 避免为运维元数据引入第七个业务文件或污染高频运行时文件。
- 主动探测只发生在用户打开页面时, 成本可控; 缓存 60s 避免手动刷新连点造成
  外部渲染服务压力。
- 「空闲」是正常状态, 与「失败」分开表达, 避免新用户没配监听就以为插件坏了。

## 后果

- 插件重载后健康历史归零, 无法做跨重启的趋势分析; 若未来需要持久化健康趋势,
  必须另立 ADR 并重新评估数据文件拓扑。
- 轮询服务需要增加埋点, 但埋点必须只记录状态、不得抛错影响轮询主链路。
- 渲染探测失败只影响健康条展示, 不阻断页面其他数据加载。
- 相关范式: `webui-config-pattern.md` (监听状态页健康条)、`docs/monitors-page-plan.md`
  (任务拆分)。
