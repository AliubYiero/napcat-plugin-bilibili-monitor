# ADR 0007: 数据文件按业务域拆分, 统一版本包裹并一次性迁移

日期: 2026-09-19
状态: 已采纳

## 背景

重构前 `store/` 下的数据文件按"数据种类"而非"业务域"切分, 同类数据散在多个
文件里: Cookie 独立、三类监听上限各占一个文件、直播监听与同接监听各占一个
文件; 动态监听记录里还混着运行时缓存 `cachedIds`。文件顶层结构也不统一, 没有
版本字段, 任何结构演进都无从判断"要不要迁移"。

## 决策

**按业务域收敛为 6 个文件, 除 Cookie 外统一 `{ version: 1, data: ... }` 包裹,
并实现一次性旧数据迁移。**

| 数据文件 | Store | 职责 |
| --- | --- | --- |
| `bilibiliCookie.json` | `BiliCookieStore` | 登录 Cookie 与用户信息 (本次不动) |
| `bilibiliLimits.json` | `BiliLimitStore` | 三类会话自定义监听上限 |
| `bilibiliLiveMonitors.json` | `BiliLiveMonitorStore` | 直播监听 + 同接监听 |
| `bilibiliDynMonitors.json` | `BiliDynMonitorStore` | 动态监听配置 |
| `bilibiliDynRuntimeData.json` | `BiliDynRuntimeStore` | 动态运行时快照 (`cachedIds`) |
| `bilibiliLiveRoomData.json` | `BiliLiveRoomStore` | 直播间运行时快照 |

配套约定:

- 数组型文件走 `BaseStore<T>`, 键值型走 `BaseRecordStore<T>`; 顶层包裹与
  解包逻辑收敛在 `store/storeFile.ts`, 读取侧兼容旧裸结构 (自愈 + 告警)。
- 迁移在 `plugin_init` 中、**任何 store 实例化之前**执行; 目标文件逐个独立
  判定幂等; 全量校验通过才写入; 失败抛错阻止插件启动。
- 执行顺序为「复制同名备份 → 写新文件 → 重命名其余旧文件」, 任一环节崩溃
  都不会丢原始数据。旧文件备份为 `<原文件名>.YYYYMMDDHHmmss.bak`。
- 不保留旧 Store 类名别名 (调用点一次性改造完成)。

## 理由

- **同类数据一个入口**: 上限、监听、运行时快照各自只有一个读写入口, 排查
  "数据存在哪、谁写的"不再需要跨文件拼图。
- **配置与运行时分离**: `cachedIds` 是每次推送都要写的高频运行时数据, 与
  低频的监听配置混在一个文件里, 写放大且语义混淆。拆开后监听配置文件的
  变更只来自用户指令。
- **版本字段是迁移的前提**: 没有 `version` 就无法区分"旧结构"与"新结构",
  也就无法安全地只迁移一次。
- **严格校验换数据可信**: 旧数据里 `uid` / `id` 若非字符串, 后续按字符串
  比较的整条链路都不可信; 与其带着脏数据运行, 不如阻止启动并要求人工处理。

## 后果

- `plugin_init` 的失败语义变了: 初始化异常不再被吞掉, 而是向上抛、阻止插件
  启动。旧文件保持原样, 新文件不写。
- 迁移只跑一次, 之后每次启动都是"读取目标文件 → 已是当前版本 → 跳过"。
- 备份文件会累积 (每次冲突追加序号), 长期运行需要人工清理。
- 无原子写 (本次非目标): 写入中断可能损坏文件; 此时读取侧会回退为空值并
  记录 error 日志, 需人工从 `.bak` 恢复。
- 未知版本 (`version` 存在但不等于 1) 的目标文件一律跳过并告警, 绝不覆盖。
- 数据文件拓扑与命名以本 ADR 为准, 后续不得自行新增或合并文件。
